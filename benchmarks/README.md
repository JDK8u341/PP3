# PP3 执行性能实测

2026-11-07，Windows 11、CPython 3.12.14、Clang 22.1.8；LLVM JIT 使用 llvmlite 0.50.0 / LLVM 22.1.0。JSON 的 Python 版本字符串仍含 `MSC`，那是已有 Python 解释器的构建信息；PP3 扩展和 AOT 确实由 Clang/LLVM 编译，字段 `native_compiler` 单独记录。

结果不是“已经接近惯用 C++ 算法”的承诺。默认原生 VM 的六个任务约为原版的 13–29 倍，LLVM JIT 在独立测量中约为原版的 15–36 倍，但相对同轮原生 VM 只快约 3%–11%。AOT 也没有稳定胜出；编译成本必须独立考虑。

## 复现

```text
python -m pip install -e ".[jit,aot]"
python benchmarks/run.py --repeat 7 --output benchmarks/results-native-windows-py312.json
python benchmarks/aot_run.py --repeat 7 --output benchmarks/results-llvm-windows-py312.json
python benchmarks/cpp_run.py
```

需要 Clang 工具链。固定输入及源程序来自本目录 [fixtures](fixtures/README.md)，不依赖在线题库。每条路线先验证 view、完整有序内存、输出、异常和字符缓冲，差分失败就停止计时。

`run.py` 每个引擎每轮清空代码缓存，cold 包含 run 内编译，hot 在同一 IR 上清空运行状态后执行。每项取 7 次中位数；短任务批量执行 2000 次降低计时器噪声。IRBuilder、Runtime 构造、进程启动与导入成本不混进热运行。

`aot_run.py` 单独统计完整 AOT 构建/载入和 JIT 准备时间；JIT 数字不含首次导入 llvmlite。每题机器码先核对全状态，再分别进行 7 次热测量。AOT JSON 中全部 `reused_artifact=false`，不是把已缓存文件加载冒充完整构建。

## 默认执行器

[完整数据](results-native-windows-py312.json)，时间单位毫秒，以下每行的加速比均来自同轮参考基线。

| 程序 | 原版 hot | auto cold | auto hot | 加速比 | 最终内存键数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| P003 十进制编解码 | 110.922 | 12.645 | 3.942 | 28.14x | 1287 |
| P004 有符号乘法 | 91.764 | 11.095 | 7.187 | 12.77x | 10936 |
| P005 GCD | 251.021 | 15.004 | 8.583 | 29.25x | 3183 |
| P006 ROT13 | 563.369 | 31.381 | 19.191 | 29.36x | 463 |
| P007 链表归并排序 | 576.083 | 29.032 | 20.800 | 27.70x | 848 |
| P008 wc | 395.943 | 44.938 | 29.241 | 13.54x | 476 |

六题关闭直接寻址。输入为 P003 `-001234`，P004 `-123,87`，P005 `-987,610`；P006 为 128 字符、P007 为 128 个逆序码点、P008 为 200 字符。完整协议内容见 `run.py`。

输出捕获到精确 StringIO；原生标准输出可以证明这里无用户回调，因而不用每个字符都物化内存。真实终端和自定义流仍保留逐字符 flush 与回调边界，速度不可直接套用此表。

微基准中，纯递减摘要能消除 200000 次迭代，约两千倍以上；这属于数学消去，不能作为一般解释器吞吐。短直线、3 次与 9 次循环仍可能慢于 ReferenceRuntime，因为检查开销超过工作量。报告保留这些不利样本。

## 真正的机器码

[Clang AOT / LLVM JIT 数据](results-llvm-windows-py312.json)。这一批测量与上一表独立，机器负载和频率有变化；不要拿不同批次的绝对时间相除。

| 程序 | 原版 ms | VM ms | AOT ms | JIT ms | AOT 准备秒 | JIT 准备秒 | JIT 相对 VM 约需回本次数 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| P003 | 109.437 | 4.407 | 4.320 | 4.165 | 33.33 | 2.662 | 10978 |
| P004 | 123.340 | 8.429 | 9.297 | 7.991 | 14.16 | 1.119 | 2560 |
| P005 | 133.455 | 4.526 | 4.488 | 4.066 | 12.96 | 0.956 | 2080 |
| P006 | 805.933 | 24.407 | 24.983 | 22.661 | 43.96 | 3.904 | 2237 |
| P007 | 758.223 | 25.343 | 26.700 | 24.577 | 35.12 | 3.457 | 4511 |
| P008 | 438.746 | 23.989 | 23.034 | 21.587 | 46.87 | 3.984 | 1659 |

回本估算为 `准备耗时 / (VM hot - 机器码 hot)`，不包括缓存文件带来的跨进程复用、首轮额外收益或不同输入分布。若机器码热运行没有更快，JSON 记为 null，不给出虚假的回本次数。微小差距易受噪声影响，不能把表中次数当作稳定阈值。

JIT 的确直接生成循环分支和小整数指令，但图访问、PyLong、状态守卫和 I/O 仍通过共享 C++ 辅助函数。当前热点已经主要花在这些工作与程序本身的大量访存上，去掉最后的 opcode 分派不会再带来一个数量级。因此默认选择原生 VM，LLVM JIT 与 AOT 显式开启。

AOT 产物约 0.3–0.7 MB/题，包含共享内核的专门化副本；相比之下 JIT 不需要每次重新编译完整 C++ 源文件。后续值得研究的是图访问基本块融合及可证明的别名/访存消除，而不是仅换一个机器码生成器。

## 惯用 C++ 参照

[C++ 数据](results-cpp-windows.json)来自 `cpp_tasks.cpp`，同样使用 Clang，正常优化，无 volatile 人为阻止优化。每批 20000 次、7 批中位数，先逐字比较输出，计时过程累加结果校验和。单位微秒：

| 程序 | 惯用 C++ 算法 |
| --- | ---: |
| P003 | 0.048 |
| P004 | 0.838 |
| P005 | 0.826 |
| P006 | 0.189 |
| P007 | 0.692 |
| P008 | 0.284 |

它只实现固定有效输入的题目算法：机器整数乘法、std::gcd、字符变换、std::sort 等；不计算 PP3 的完整可见内存，不模拟每字符 flush，不含进程启动、协议读取和 Python 回调。这是更窄任务的性能参照，不是语义等价的另一个后端。

差距仍有多个数量级。例如 P004 的 PP3 程序需要保留 10936 个地址的最终状态，而直接 C++ 乘法只需两个数和一个结果。把前者替换为后者将改变公开 memory，不能在本任务“语义兼容”的限制下伪称等价优化。即使只比较核心计算，当前原生图辅助函数和 DSL 算法仍有优化空间。

## 验证边界

CI 在 Linux/Windows × Python 3.10/3.12/3.14 检查原生、AOT、JIT、纯 Python 回退；JIT 另对全部 20 个归档程序和各测试输入逐项对照。性能数字来自本机而非共享 CI，CI 不设速度阈值。

不同 CPU、系统负载、输入规模、终端类型、Python 版本和编译器都会改变结果。短程序回退开销、大整数慢路径、宿主回调和并发同步限制见[执行器设计](../docs/executor.md)。早期 Python 专用后端的独立历史测量保存在 [results-windows-py312.json](results-windows-py312.json)，不与本次不同负载时段的毫秒数直接比较。
